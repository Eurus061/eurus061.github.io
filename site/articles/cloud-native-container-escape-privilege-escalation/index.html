云原生安全：从容器隔离到逃逸与权限扩散

从 Linux 权限和容器隔离机制出发，梳理容器逃逸、宿主机提权、跨租户访问与 Kubernetes 权限扩散，建立分析攻击链、判断证据和设计防护的完整框架。

Jester2026.10.27约 23 分钟

容器逃逸的文章经常从一条命令、一个危险挂载或一个 CVE 开始。这样的材料容易帮助读者复现某种现象，却未必能回答更基础的问题：容器到底隔离了什么？拿到容器内的 root 之后，距离控制宿主机还有多远？为什么有些攻击没有进入宿主机，仍然能影响其他租户甚至业务后台？

理解这些问题，需要把 Linux 权限、容器运行时、Kubernetes 授权和业务身份放在同一张图里。本文按“系统组成 → 隔离机制 → 越界路径 → 权限扩散 → 证据与防护”的顺序展开，重点解释每一步跨越的边界，以及结论成立所需的条件。

文中的案例是为解释机制构造的通用示意场景，路径和角色均为示例。配置片段用于说明设计思路，具体行为仍取决于实际内核、运行时版本和部署策略。

一、先画出系统：容器外面还有什么

在常见的 Kubernetes 环境中，用于安全分析的系统关系可以简化为：

Kubernetes 控制平面
  └─ API、授权、准入与调度

运行节点
  ├─ 容器运行时：创建和管理容器进程
  ├─ Pod：承载应用进程
  └─ 存储、网络、日志、备份与诊断服务

共享存储和业务身份体系可能跨越多个节点

传统 Linux 容器中的应用通常直接通过系统调用与共享内核交互，容器运行时主要负责生命周期管理。安全分析需要同时审视下面几类对象。

对象 主要职责 安全分析关注点
容器进程 执行业务代码 进程身份、系统调用、文件和网络访问
Pod 组织共享部分运行环境的容器 容器间共享资源、挂载与服务账号
Node 运行 Pod 的节点，可以是物理机或虚拟机 宿主机权限、节点凭据、同节点工作负载
容器运行时 创建、启动和管理容器 管理接口、执行上下文与运行时漏洞
控制平面 提供 API、调度和集群状态管理 身份认证、授权和准入控制
存储与辅助服务 提供共享目录、日志、备份、诊断等能力 是否会替低权限进程执行高权限操作

分析时尤其要注意最后一行。一个容器的安全边界，除了运行时自身，还包括所有能够读取容器数据、解释容器输入、代替容器执行操作的服务。

例如，日志收集器读取应用日志，备份服务遍历工作目录，故障诊断程序处理崩溃进程的信息。这些组件的运行权限通常高于业务进程，因而也可能成为权限跨越的中间环节。

二、容器隔离由多种机制共同组成

传统 Linux 容器通常共享宿主机内核。容器看到的独立进程列表、文件系统和网络环境，是内核隔离机制与运行时配置共同形成的结果。Docker 安全说明

理解这些机制时，可以先给每一种机制分配一个明确的问题。

机制 主要回答的问题 不能据此推导的结论
Namespaces 进程能看到哪一组系统资源？ 有独立视图就能抵御所有内核漏洞
Cgroups 一组进程可以使用多少资源？ 限制 CPU、内存就完成了权限隔离
UID/GID、DAC 与 ACL 当前身份能访问哪些文件？ 目录名不同就形成可靠的租户边界
Capabilities 当前线程拥有哪些特权能力？ UID 为 0 就拥有全部特权
Seccomp 哪些系统调用被允许？ 加载了过滤器就足以阻止所有逃逸
AppArmor / SELinux 当前进程还受哪些强制访问策略约束？ 仅看文件权限就能判断最终访问结果

2.1 Namespace 隔离的是资源视图

常见的 namespace 包括：

  • Mount namespace：隔离挂载表和文件系统视图。
  • PID namespace：隔离进程编号与可见范围。
  • Network namespace：隔离网络设备、路由和端口等资源。
  • User namespace：隔离用户、组及相关权限上下文，并支持身份映射。

独立的 mount namespace 不意味着所有数据都私有。运行时仍然可以把同一份宿主机目录挂进多个容器。独立的 PID namespace 也不会自动改变底层共享内核这一事实。Linux namespaces 手册

这里还存在一个术语陷阱：Linux namespace 和 Kubernetes Namespace 是两种不同的机制。 前者属于内核资源隔离；后者用于组织集群 API 对象。Kubernetes 的多租户隔离还需要 RBAC、网络、存储和工作负载策略共同落实。Kubernetes 多租户文档

2.2 隔离策略必须结合资源暴露面理解

假设两个容器都采用独立的 mount namespace，但其中一个挂载了宿主机管理套接字，另一个只挂载自己的只读配置。两者表面上都“在容器里”，实际可触达的管理能力却可能相差很大。

因此，判断隔离强度至少要同时看三件事：资源是否暴露、进程具备什么权限、后续操作受到什么策略限制。

三、容器内的 root，究竟意味着什么

id 显示 uid=0，说明当前进程在所在 user namespace 中拥有 UID 0。要判断这个身份对宿主机意味着什么，还需要检查 UID 映射、capabilities、挂载和强制访问控制。Linux user namespaces 手册

3.1 UID 映射决定身份如何对应

在没有额外 user namespace 映射的常见部署中，容器 UID 0 可以对应宿主机 UID 0，但进程仍可能受到能力裁剪、独立挂载视图和其他策略的限制。

启用 UID 映射后，容器里的 UID 0 可以对应宿主机上的某个普通 UID。它仍然在自己的命名空间内表现为 root，却不会因此获得宿主机初始 user namespace 中的同等权限。

这也解释了三种配置为什么不能混用概念。

配置 改变了什么 仍需关注什么
容器内使用非 root 用户 降低应用进程的运行权限 宿主机管理接口、共享存储、内核和辅助服务
userns-remap 将容器 UID/GID 映射到宿主机其他身份 Docker daemon 仍可能以宿主机 root 运行
Rootless Docker daemon 与容器都在非宿主机 root 的权限体系下运行 用户可访问的资源、内核风险及部署兼容性

后两者的区别可参见 Docker UID 映射说明 和 Rootless 模式文档。

3.2 Capabilities 决定具体的特权操作

Linux 把传统 root 的部分权限拆分为 capabilities。例如：

能力 与安全分析相关的含义
CAP_DAC_OVERRIDE 可以绕过部分传统文件读写与执行权限检查
CAP_SYS_PTRACE 涉及进程跟踪等操作，仍需结合目标可见性与其他检查
CAP_NET_ADMIN 涉及相关网络命名空间内的多类管理操作
CAP_SYS_ADMIN 覆盖大量管理操作，授权范围很广

能力的效果还受到 user namespace 归属和内核检查位置影响。看到 CAP_SYS_ADMIN 应当提高警惕，但不能跳过具体条件，直接宣称已经取得宿主机控制权。Linux capabilities 手册

3.3 逃逸不一定以容器 root 为前提

如果低权限进程可以调用一个存在漏洞的宿主机高权限服务，越界动作可能由那个服务完成。攻击者不必先在容器内提权到 root。

反过来，即使容器内已经是 root，只要缺少可用的越界路径，也不能由此确认宿主机失陷。身份、能力和跨边界路径，需要分别分析。

四、把“执行、提权、逃逸、接管”拆成不同结论

安全报告中的几个词经常出现在同一条攻击链里，但它们描述的是不同的事实。

概念 已经证明的事实 还不能自动证明什么
容器内代码执行 可以在目标容器的权限上下文中运行代码 已经进入宿主机
容器内提权 从容器内低权限身份获得更高权限 已获得宿主机初始命名空间的权限
跨租户访问 越过租户授权边界访问其他租户资源 已经在宿主机执行命令
容器逃逸 越过预期隔离边界，获得容器外的资源访问或执行能力 已经控制整个节点或集群
宿主机提权 在节点操作系统中获得更高权限 已拥有集群管理员权限
集群权限提升 获得超出原授权范围的 Kubernetes 管理能力 已控制所有业务身份体系
横向移动 从当前资源继续进入其他工作负载、节点或服务 所有后续目标都已被实际控制

“逃逸”的使用口径需要写清楚。越界读取宿主机文件与在宿主机执行任意命令，都可能被归入逃逸，但两者的能力和后续条件不同。

一条可能的路径是：

应用代码执行
  → 越过容器隔离
  → 获取节点权限
  → 接触可用凭据
  → 以某个身份调用 Kubernetes API
  → 在授权和准入允许的范围内继续扩散

还可能出现另一条路径：

容器内低权限进程
  → 借助高权限辅助服务读取其他租户文件
  → 获得业务身份材料
  → 访问该身份被允许访问的业务系统

第二条路径可以完全绕过“宿主机 shell”这一环。分析工作应当围绕实际跨越的边界展开，避免把所有结果都压缩成一个“拿下”。

五、常见越界路径：先找边界，再看漏洞

从机制上，可以把常见路径分为六类。

路径 核心前提 跨越的主要边界
危险运行配置 过量 capabilities、敏感 hostPath、设备或宿主机命名空间暴露 容器进程到宿主机资源
管理接口暴露 能访问具备管理权的运行时套接字或服务 普通工作负载到容器管理平面
高权限辅助服务缺陷 日志、备份、诊断程序处理不可信输入 低权限调用者到高权限代理
运行时漏洞 容器创建或执行阶段存在隔离缺陷 容器执行上下文到宿主机上下文
内核漏洞 共享内核存在可利用缺陷且满足前提 受限进程到更高内核权限
身份与授权缺陷 令牌暴露、角色过大或主体绑定错误 当前身份到其他管理权限或租户身份

前几类常被归入传统容器逃逸。最后一类可能没有突破内核或运行时隔离，却同样会扩大影响。

5.1 危险配置会让隔离边界变薄

敏感宿主机目录的可写挂载、过量设备访问和特权模式，都会显著改变工作负载的可操作范围。privileged: true 涉及广泛提权，也会改变 seccomp、AppArmor、SELinux 等约束的应用方式，不能理解为简单地“换成 root 用户”。Kubernetes 内核安全约束说明

但 hostNetwork: true、hostPID: true 和特权容器分别暴露不同资源，不能用同一套推断替代逐项检查。

5.2 管理套接字本身可能就是高权限入口

能够向 rootful Docker daemon 发送具有管理权限的请求，通常意味着可以影响由它管理的容器和宿主机资源。Docker 官方明确指出，docker 组具有 root 级别权限。Docker 安装后的 Linux 配置说明

因此，把管理套接字挂进普通业务容器，等于把一部分管理能力带入业务信任域。具体影响还要看 daemon 身份、接口授权、代理过滤和可执行操作。

5.3 运行时漏洞会在生命周期切换时破坏隔离

以公开的 CVE-2024-21626 为例，runc 内部文件描述符泄露可能使容器进程获得指向宿主机文件系统的工作目录，并在特定条件下形成逃逸。这类问题提示我们：风险也可能出现在容器创建、工作目录设置和进程执行阶段。runc 官方安全公告

这里引用历史漏洞是为了说明机制。生产修复应核对当前发行版的安全公告与补丁状态，不能把某个历史修复版本当作长期升级目标。

六、典型场景一：高权限服务替低权限进程越权读文件

考虑一个提供多租户工作目录的平台。租户 A 只能读取自己的目录，但节点上的诊断服务可以访问更大的共享存储范围。

正常设计中，诊断服务接收租户工作目录中的一个文件，将它复制到诊断输出目录。风险会出现在下面几步同时成立时：

  1. 租户可以控制服务将要读取的路径或目录项。
  2. 这个路径能通过符号链接或其他解析行为指向租户范围外的文件。
  3. 高权限服务打开文件时，没有把最终目标约束在调用者的授权范围内。
  4. 复制结果又被放进调用者可以读取的位置。
租户 A 控制路径
      ↓
诊断服务以更高权限解析并打开路径
      ↓
实际读到了租户 B 的文件
      ↓
结果复制到 A 可读的输出目录

这属于 Confused Deputy，混淆代理问题：代理具备合法权限，却没有正确核实本次操作是否也被调用者授权，最终替低权限主体完成了越权动作。

6.1 关键在于谁打开文件，以及最终打开了什么

符号链接本身不会赋予调用者读取目标文件的权限。风险来自执行文件打开操作的主体发生了变化：低权限进程无法直接读取的文件，可能被高权限服务读出并重新输出。

因此，这类问题不一定说明底层文件系统的 ACL 实现失效。文件系统可能严格按照“高权限服务”的身份完成了访问检查，而漏洞位于上层服务的授权与路径处理。

6.2 路径检查需要覆盖解析过程

仅做字符串前缀匹配很容易漏掉路径解析语义。先检查、再按路径重新打开，还可能遇到检查与使用之间目录项被替换的竞态。

在 Linux 上，openat2() 提供 RESOLVE_BENEATH、RESOLVE_IN_ROOT、RESOLVE_NO_SYMLINKS 等解析约束，可以围绕可信目录描述符限制目标路径。它们有不同语义，部分选项不能组合，应按业务允许的链接行为选用，并避免后续再次进行不受约束的路径打开。openat2 手册

修复还应覆盖服务身份、存储授权和输出文件权限。仅拦住某一种符号链接写法，未必能修复整个代理越权问题。

6.3 共享文件系统要单独审视授权模型

共享存储的访问结果可能同时受 Linux UID/GID、ACL、挂载凭据和存储服务端授权影响。目录采用随机名称，只能降低猜测概率，不能替代访问控制。

以 CephFS 为例，客户端可以配置路径范围的 capabilities。另一个容易误解的细节是：CephFS 的 root_squash 主要限制 root 客户端的写操作，仍允许其读取；因此它不能独立解决这类跨租户读取风险。CephFS 客户端权限文档

七、典型场景二：崩溃处理程序成为宿主机执行入口

Linux 可以通过 core_pattern 将 core dump 交给一个用户态程序处理。采用以 | 开头的管道形式时，内核启动的处理程序默认以 root 用户和组运行，并处于初始命名空间中；LSM 等安全约束仍然有效。Linux core 手册

这是一项正常的故障诊断能力。风险发生在处理程序把来自低信任进程的数据，错误地当成高权限操作指令时。

假设处理程序为了收集诊断材料，主动读取崩溃进程的环境、文件名或工作目录信息，随后把某个字段拼接进 shell 命令。若攻击者能控制该字段，输入就可能从“待处理数据”变成“命令语法”。

低权限进程控制部分输入
      ↓
符合条件的崩溃触发诊断流程
      ↓
宿主机处理程序读取不可信数据
      ↓
数据被拼入 shell 命令
      ↓
命令在处理程序的权限上下文中执行

7.1 内核机制与处理程序漏洞要分开

环境变量不会因为进程崩溃就自动被内核作为 shell 命令执行。这里的危险步骤，是辅助程序主动读取数据并进行不安全解释。

同样，容器能够触发自己的进程崩溃，不代表一定能逃逸。攻击链还要求处理流程可触达、危险字段可控、命令构造确有缺陷，并且执行上下文具备相应权限。

7.2 防护要覆盖输入到执行的全过程

可靠的处理方式包括：避免 shell 字符串拼接，采用固定可执行文件与参数数组；对参数值、选项和资源范围进行验证；限制继承环境；拆分必须高权限执行与可降权执行的步骤；让输出只对相应租户可读。

使用参数数组可以去掉 shell 解释这一层风险，但仍应防止参数注入、危险子命令和越界路径。代码采用了 shell=False，并不等于调用行为已经安全。

八、典型场景三：从文件访问扩展到身份与集群权限

越界读取的影响取决于读到什么。普通业务文件、工作负载令牌和可用于换取身份的材料，后续可产生的能力不同。

8.1 三套身份体系需要分别分析

身份体系 常见身份材料 主要决定什么
Linux 身份 UID/GID、capabilities、进程凭据 操作系统资源访问
Kubernetes 身份 ServiceAccount 令牌、客户端证书等 API 中允许执行的资源操作
业务身份 SSO 会话、业务 access token 等 业务系统中的账号与角色

Linux root 不等于 Kubernetes cluster-admin。拿到业务令牌，也不意味着拥有其他业务系统的任意权限。系统之间若存在换取令牌、代理调用或身份映射，还需要继续验证这些桥接关系。

尤其要核对：服务端是否把请求中的用户名与已认证主体绑定。用户提交的 username 只能视为输入，不能直接成为操作身份。实际授权应依赖可信会话或令牌主体，并针对目标资源再次检查。

8.2 ServiceAccount 令牌的效力取决于授权

工作负载可能通过投射卷获得具有生命周期和受众约束的 ServiceAccount 令牌。一个令牌能否使用，要看有效期、受众与服务端验证；能做什么，则取决于该身份获得的授权。Kubernetes ServiceAccount 文档

因此，“发现了 token 文件”和“获得集群管理员权限”之间，至少还隔着身份有效性、API 可达性和授权范围几层判断。

8.3 工作负载创建权限可能带来间接能力

RBAC 审查不能只看有没有 cluster-admin。能够创建 Pod 或工作负载，可能进一步接触同命名空间的 Secrets、存储和其他 ServiceAccount 的身份；list、watch Secrets 也可能返回其内容。Kubernetes RBAC 最佳实践

这种间接能力是否可用，还受到准入、工作负载策略及具体资源配置限制。例如，创建普通 Pod 的权限，不能在缺少相应准入许可时直接等同于创建特权 Pod 的能力。

8.4 节点失陷到集群接管，仍有缺失条件需要补齐

节点 root 往往能够接触该节点上的工作负载文件、运行状态或身份材料，风险很高。但继续影响其他节点，通常仍需要可用凭据、足够授权、网络可达性以及被允许的执行途径。

Kubernetes 的 Node authorizer 对节点身份有专门的授权模型，不能把一个节点证书直接视为任意集群管理凭据。Kubernetes 节点授权文档

对影响范围，应分别记录“当前已控制”“具备明确可达路径”和“尚未验证”的资源。测试环境中的结果，也不能直接作为生产环境已经失陷的证据。

九、Agent 沙箱：内容审查与运行隔离各自负责什么

当应用可以运行模型生成代码、调用工具或安装技能时，容器的隔离对象变成了更不可信、变化更频繁的程序内容。

这里有两条独立的防线。

内容与供应链防线关注：工具和技能来自哪里，审核的是哪个版本，审核后内容能否被替换，执行时是否校验同一份产物。

执行与授权防线关注：程序最终以什么身份运行，可以访问哪些挂载、网络和令牌，以及会把什么输入传给宿主机服务。

如果只审核了一份入口说明，执行时却可以下载另一份脚本，审核与实际执行对象之间就出现了断裂。即使内容审查有效，也不应以此替代运行时隔离；模型答复“已遵守限制”，同样不能证明底层操作没有越界。

对需要运行不可信代码的多租户平台，应当将这些程序纳入明确的威胁模型，并按实际能力设置隔离和授权边界。

十、如何判断证据：从风险线索到可验证结论

识别危险配置和证明实际越界，是两项不同工作。

下面是一组用于 Linux 容器环境初步观察的只读命令，可以帮助建立运行上下文。它们提供的是当前可见信息；仍需与宿主机、运行时配置和控制平面记录交叉核对。

id
cat /proc/self/uid_map
readlink /proc/self/ns/user /proc/self/ns/mnt /proc/self/ns/pid
awk '/^(Uid|Gid|CapEff|CapBnd|NoNewPrivs|Seccomp):/' /proc/$$/status
cat /proc/self/mountinfo
cat /proc/sys/kernel/core_pattern

10.1 常见输出能说明什么

观察 可以支持的判断 不能单独支持的判断
uid=0 当前命名空间中的 UID 为 0 已获得宿主机管理权限
CapEff 含高风险能力 当前有效能力集包含该位 存在可用的逃逸路径
Seccomp: 2 当前进程处于 seccomp 过滤模式 过滤规则充分且不可绕过
NoNewPrivs: 1 已设置 no_new_privs 标志 不会出现任何形式的权限扩散
看见宿主机路径挂载 资源已进入当前挂载视图 可写、可利用或属于未授权访问
core_pattern 指向管道处理程序 存在相应崩溃处理机制 处理程序存在命令注入漏洞

在容器内部比较 namespace 链接，还需要可信的宿主机参照。容器里的 PID 1 往往也是容器进程，不能默认把它当作宿主机 PID 1。

10.2 一个标记文件不足以证明宿主机执行

如果某个目录本来就是可写共享挂载，容器内的进程可能直接在其中创建文件。文件随后出现在宿主机，甚至显示为 root 所有，并不能单独证明创建它的命令已经在宿主机执行。

更完整的证据应把这些信息连接起来：触发请求、进程父子关系、实际 UID 与命名空间、执行审计记录，以及受控目标上的副作用。关键是排除“容器原本就具备这项权限”的解释。

10.3 结论应当与证据对应

一份便于复核的分析可以按以下顺序组织：

  1. 起点权限：攻击者最初能控制什么。
  2. 越界入口：哪项服务或机制接收了不可信输入。
  3. 权限转换：哪个主体替谁执行了什么操作。
  4. 可观察结果：具体访问或执行能力如何被证明。
  5. 影响边界：涉及哪些身份、资源与环境。
  6. 修复与复测：在哪个环节阻断路径，以及如何确认阻断有效。

这套结构也适合阅读公开漏洞分析：如果“某节点执行成功”之后直接跳到“全部集群接管”，中间缺少的通常就是身份、授权和执行范围的证据。

十一、把防护措施放回攻击链

防护配置需要解释自己阻断的是哪一步。否则容易出现基线项都勾选了，辅助服务仍然替租户越权访问的情况。

环节 主要控制措施 需要持续核对的边界
不可信代码进入 固定产物、校验完整性、审查执行内容 审核版本与运行版本是否一致
容器内运行 非 root、能力裁剪、seccomp、LSM 工作负载真实生效的运行配置
访问宿主机 限制特权、hostPath、设备和管理套接字 暴露资源是否超出业务需要
调用辅助服务 降权、参数验证、受约束路径打开 服务是否继承调用者的授权范围
读写共享存储 租户范围授权、隔离挂载与输出 客户端凭据和服务端权限是否过大
使用工作负载身份 最小 RBAC、受众和有效期约束 令牌是否可被无关任务读取和使用
向集群扩散 准入控制、网络策略、节点隔离 创建工作负载带来的间接权限
进入业务系统 认证主体绑定、资源级鉴权、凭据吊销 代理调用是否发生身份混淆

11.1 一个基础的工作负载约束片段

下面是 Pod 配置中的安全相关片段，省略了镜像、业务端口和其他字段：

spec:
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      securityContext:
        privileged: false
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]

使用前应确认镜像支持指定 UID，业务所需写目录已经通过适当卷提供。如果程序确实需要调用 Kubernetes API，可以按需提供权限受限的身份，而不是机械关闭后再换成更大的凭据。Kubernetes 安全上下文配置

allowPrivilegeEscalation: false 对应 Linux 的 no_new_privs 约束，主要阻止通过后续 execve 获得额外权限，例如 setuid 或文件 capabilities。它不会撤销已有权限，也不会自动修复一个可被调用的高权限服务。Linux no_new_privs 文档

11.2 准入基线与系统安全各有覆盖范围

Kubernetes Pod Security Standards 的 Restricted 级别，对非 root、能力裁剪、提权限制和 seccomp 等提出了约束，可以作为工作负载准入的重要基线。具体适用条件需要结合操作系统和采用的策略版本核对。Pod Security Standards

它不能独立解决共享文件系统的租户授权、宿主机诊断脚本的命令构造，或业务 API 的身份绑定错误。这些仍需在相应组件中修复。

11.3 更强隔离适用于更强的威胁模型

对于不可信代码和多租户执行平台，可以评估额外隔离层。gVisor 通过用户态应用内核处理大量系统调用；Kata Containers 通过轻量虚拟机提供基于虚拟化的工作负载隔离。gVisor 文档、Kata Containers 项目说明

选择时还需要验证兼容性、性能、设备需求与运维成本。即使执行边界更强，把所有租户的文件或高权限令牌主动交给同一个工作负载，也依然会带来数据和授权风险。

十二、建立一条可持续深化的学习路线

学习容器逃逸时，可以把“会复现一个漏洞”放在更完整的知识结构中检验。

阶段 核心内容 应能独立回答的问题
Linux 权限 UID/GID、DAC、ACL、capabilities、进程凭据 一个进程为什么能打开某个文件？
容器隔离 namespaces、cgroups、seccomp、LSM、挂载 当前进程看到什么，又被允许做什么？
运行时与节点 OCI、运行时管理接口、容器生命周期、宿主机服务 哪个组件在哪个权限上下文中执行操作？
Kubernetes 授权 ServiceAccount、RBAC、准入、Pod 安全策略 一个身份能否通过创建工作负载获得间接能力？
多租户与身份 共享存储、代理授权、业务令牌、身份映射 哪个边界失效会把单租户问题扩展到其他主体？
证据与防护 进程上下文、审计、受控副作用、修复复测 已经证明的能力与尚未验证的影响分别是什么？

沿着这条路线阅读漏洞文章时，可以始终记录一组信息：起点主体、可控输入、代执行者、权限上下文、目标资源、可观察结果。这些信息齐全后，配置错误、运行时漏洞、辅助服务缺陷与身份越权之间的联系才会逐渐清晰。

云原生环境中的权限扩散，常常发生在组件之间的交接处：路径交给文件服务，进程信息交给诊断程序，凭据交给 API，请求中的账号交给业务代理。审视这些交接，能够帮助我们从单个漏洞走向对整个系统安全边界的理解。
